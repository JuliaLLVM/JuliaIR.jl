JuliaMultiVersioning

Julia's system and package images run on many CPUs, but code compiled for a recent CPU's features runs faster on that CPU. When Julia builds an image for several targets (the JULIA_CPU_TARGET environment variable, or --cpu-target), its JuliaMultiVersioning pass compiles the image's functions once per target where that pays off, and emits tables from which Julia's image loader picks, for the CPU it runs on, a version of each function.

jl-multiversioning (JuliaIR.MultiVersioningPass) ports the pass for the IR of every Julia version from 1.10 on, and jlopt runs it for Julia's name of the pass (JuliaMultiVersioning, also JuliaMultiVersioning<external>). It is a required module pass, which does nothing unless the module has the julia.mv.enable module flag. The code keeps the names and the structure of the C++ (annotate_module_clones, CloneCtx, prepare_slots!, clone_bodies!, fix_gv_uses!, fix_inst_uses!, emit_metadata!, ...), so that both can be read side by side.

Targets

The targets are listed in the julia.mv.specs module flag, which Julia sets when it builds an image: a CPU name, the target features to add, the index of a base target and flags. JuliaIR.target_specs reads them as JuliaIR.MultiVersioningTargets. The first target is the one the image needs at least; a target either clones every function (clone_all), or only the functions that benefit from its features (its clone categories), and uses the versions of its base target (the first target, or one that clones every function) for the others. For modules without the flag, the targets keyword of MultiVersioningPass gives them (a non-empty vector; by default nothing, the module's), and the pass records them in the flag.

What the pass does

  1. Annotation. Julia annotates its modules before it runs the pass (which marks them with the julia.mv.annotated flag); for other modules, the pass does it. Each function that is cloned gets a julia.mv.clones attribute, the set of targets to clone it for: targets that clone everything, and targets whose categories the function matches (loops, vector arguments or results, fast or fused floating-point math, queries of CPU features, half or bfloat values, as the target says), together with the functions between them in the call graph. A function gets a relocation slot (julia.mv.reloc) if instructions use it and a selective target clones it, or if an alias names it. Other functions in global initializers are marked julia.mv.fvar. With the julia.mv.skipcloning flag, the pass stops here.
  2. Cloning. Each function is cloned for its targets (f.1, f.2, ... after the targets' indices), with the target's CPU and features, optsize or minsize if the target says so (unless the function is optnone), and a julia.mv.clone attribute with the target's index.
  3. Uses. Calls (and other uses by instructions) from a version of a function to a function that some targets of its group clone load the callee from its relocation slot, which the loader fills in with the version it picks. Uses in global initializers become null, and relocations: entries telling the loader to write the picked version there. Aliases of cloned functions become trampolines, functions that call the function through its slot.
  4. Tables. The pass replaces Julia's table of the image's functions (jl_fvars) by the tables the loader reads: the functions (jl_fvar_*), the relocations (jl_clone_slots), and per target the functions it has a version of (jl_clone_idxs) and those versions (jl_clone_ptrs, or jl_clone_offsets). The julia.mv.suffix module flag is appended to their names.

Differences from the C++ pass

The port fixes these issues in Julia's C++ pass:

  • Call-graph expansion. The C++ pass extends the set of functions to clone in the order of their addresses in memory, without revisiting functions, so that whether a function between cloned ones is cloned can differ from one run to the next. The port extends the set until it contains every function that is called by and calls a function in it, which includes everything the C++ pass may clone.
  • Trampolines' ABI. Before Julia 1.13, trampolines call the function without its calling convention and its parameter and return attributes (like byval and sret), which passes the arguments wrong. The port keeps them for every version, like Julia 1.13 does.
  • 32-bit IR on Julia 1.10. Julia 1.10 truncates the tables' offsets according to the pointer size of the machine it runs on, which emits invalid IR for 32-bit targets on 64-bit machines. The port goes by the module's pointer size, like later versions.
  • Uses of aliases. The C++ pass erases the aliases it replaces by trampolines with their uses, which leaves those dangling; the port redirects them to the trampolines.
  • Duplicate julia.mv.veccall flags. When it annotates a module that already has the flag, the C++ pass adds a second one, which makes the module invalid. The port keeps an identical flag, and rejects a different one.
  • external. For reduced test cases, external tolerates function tables with entries that aren't function definitions: the C++ pass drops every entry after the first of them, the port only those entries.
  • Malformed input. Where the C++ pass asserts, crashes or emits wrong code (no jl_fvars or jl_fvar_idxs table, an index table with fewer 32-bit entries than the loader reads, malformed target flags or julia.mv.clones attributes, functions without a version for a target that clones everything, a relocated function that isn't in the function table, a target based on one that doesn't clone everything, a cloned function in a constant global, in llvm.used, under an expression that changes its address (including a cast to an integer of another size, where the loader would write a full pointer over what follows), or used by a global value other than a global variable or an alias, a cloned function's exception handling instruction that would have to load a function from its slot, ...), the port throws a JuliaIR.MultiVersioningError before it changes the module.

Julia runs the pass after the always-inliner, which removes the available_externally copies of alwaysinline functions that the partitions of an image get from each other. Run before it, the pass rejects them when they are relocated: they need a slot, but aren't in the partition's function table (the C++ pass reads a garbage index for them).

Functions without a julia.mv.clones attribute call the first target's versions, even when other targets have clones. Variadic trampolines use musttail calls on every architecture, as in Julia's release builds; assertion builds reject them on ARM and PowerPC.
