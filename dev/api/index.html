API reference

The API is not exported; use qualified names (JuliaIR.register!).

Passes

JuliaIR.register! — Function
JuliaIR.register!(pb::PassBuilder; fp16=:auto, bf16=:auto, gc_barrier=:stock)

Register every pass of this package with the pass builder pb, so that they can be used by name in its pipeline. The keyword arguments are the defaults of the policy options for occurrences of the passes that do not specify them (see JuliaIR.Dialect).

JuliaIR.passes()

The names of the passes of this package, as used in pipelines.

JuliaIR.RemoveNIPass — Function
JuliaIR.RemoveNIPass()

Remove the non-integral address spaces from the data layout of a module (jl-remove-ni in a pipeline). Needed before code generation by back-ends that don't support non-integral pointers.

source
JuliaIR.AllocOptPass — Function
JuliaIR.AllocOptPass()

Remove Julia GC allocations whose object does not escape, or move them to the stack, whole or split into their fields (jl-alloc-opt in a pipeline).

source
JuliaIR.PropagateAddrspacesPass — Function
JuliaIR.PropagateAddrspacesPass()

Make loads, stores, atomics and memory intrinsics that access memory through one of Julia's special address spaces use the untracked pointer the address was derived from, when that pointer can be recovered through address space casts, GEPs, phis and selects (jl-propagate-addrspaces in a pipeline). Run dce or another cleanup afterwards to remove the instructions that became unused. Like Julia's C++ pass, it is required, so it also runs on optnone functions.

source
JuliaIR.DemoteFloat16Pass — Function
JuliaIR.DemoteFloat16Pass(; fp16=:auto, bf16=:auto)

Perform floating-point arithmetic on half (fp16) and bfloat (bf16) values in float, truncating every result, so that the IEEE semantics of the 16-bit types are preserved on targets that don't support them natively (jl-demote-float16 in a pipeline). Whether a type is demoted is decided by the policies: :demote and :keep apply to every function, :auto follows the rule of the Julia version, which reads the function's target-features (Julia 1.10, 1.11) or julia.hasfp16/julia.hasbf16 attributes (1.12 and later; without them, half is demoted only on PowerPC and bfloat is kept). Operations with all fast-math flags are left alone.

Meant to run late in the pipeline, not followed by instcombine (which would fold the conversions away); gvn can clean up redundant conversions. Like Julia's C++ pass, it is required, so it also runs on optnone functions, whose semantics it affects.

source
JuliaIR.GCInvariantVerifierPass — Function
JuliaIR.GCInvariantVerifierPass(; strong=false)

Check that functions obey the invariants of Julia's GC address spaces (jl-gc-invariant-verifier in a pipeline, jl-gc-invariant-verifier<strong> for strong=true), and throw a JuliaIR.GCInvariantError listing every violation otherwise. strong also rejects GEPs of tracked pointers, which Julia's code generator never emits but the optimizer may introduce.

JuliaIR.GCInvariantError

The error thrown by GCInvariantVerifier (jl-gc-invariant-verifier) when a function violates GC invariants. violations lists every violation found in the function, in the order of its instructions, as JuliaIR.GCInvariantViolations.

source
JuliaIR.GCInvariantViolation — Type
JuliaIR.GCInvariantViolation

One violation of a GC invariant found by GCInvariantVerifier: the message that says which invariant, and the offending instruction, as text.

source
JuliaIR.LateLowerGCFramePass — Function
JuliaIR.LateLowerGCFramePass(; gc_barrier=:stock, task_gcstack=0, task_ptls=0,
                             tls_safepoint=0, tls_gc_state=0)

Julia's GC root placement (jl-late-lower-gc-frame in a pipeline, LateLowerGCFrame in Julia's pipelines): roots the values in Julia's tracked address spaces that are live at a safepoint in a GC frame, and lowers Julia's GC intrinsics, allocations, write barriers and operand bundles for its runtime. See the documentation for what it does on each Julia version.

Lowering allocations and GC state transitions needs the layout of the runtime's task and thread-local state, which is taken from the running Julia (see JuliaIR.runtime_layout) only for functions that need it. The other keyword arguments give these offsets explicitly.

source
JuliaIR.LateGCCleanupPass — Function
JuliaIR.LateGCCleanupPass()

JuliaIR.LateLowerGCFramePass for functions without a GC frame (jl-late-gc-cleanup in a pipeline), as GPU back-ends emit them: the part of Julia's LateLowerGCFrame pass that applies to GPU code. See the input contract in the documentation; functions that need Julia's runtime or a GC frame make the pass throw a JuliaIR.UnsupportedInputError before anything is changed.

source
JuliaIR.CombineMulAddPass — Function
JuliaIR.CombineMulAddPass()

Allow the back-end to fuse a multiplication and the addition or subtraction it feeds into a multiply-add (jl-combine-muladd in a pipeline): when an fadd or fsub has the contract fast-math flag and one of its operands is an fmul without other uses, that fmul is marked contract too (if both operands qualify, only the first). Julia 1.12 removed the pass, so it does nothing for the IR of Julia 1.12 and later. Like Julia's C++ pass, it is skipped on optnone functions.

source
JuliaIR.UnsupportedInputError — Type
JuliaIR.UnsupportedInputError

The error thrown by LateGCCleanup (jl-late-gc-cleanup) when a function contains constructs that need Julia's runtime or a GC frame (see the input contract in the documentation). constructs lists all of them, as JuliaIR.UnsupportedConstructs, in the order of the function's instructions. The function is not changed.

source
JuliaIR.UnsupportedConstruct — Type
JuliaIR.UnsupportedConstruct

A construct that LateGCCleanup (jl-late-gc-cleanup) does not support: the message that names it, the offending instruction (or argument) as text, and its source location (file:line, or empty without debug information).

source
JuliaIR.LowerExcHandlersPass — Function
JuliaIR.LowerExcHandlersPass(; handler_size=0, handler_align=0, setjmp="",
                             setjmp_savemask=:auto)

Lower Julia's exception handlers (julia.except_enter and the matching jl_pop_handler calls) to calls of the runtime's jl_enter_handler and setjmp on stack buffers (jl-lower-exc-handlers in a pipeline). Only Julia 1.10 to 1.12 emit these; for later dialects the pass does nothing.

The lowering depends on the Julia runtime the code will run with (the size of its exception handler structure and the name of its setjmp), which is taken from the running Julia (see JuliaIR.runtime_layout), only for functions that have handlers; handler_size, handler_align and setjmp give these facts explicitly. Like Julia's pass, setjmp is called with a savemask argument unless the module's triple is for Windows; setjmp_savemask (:yes or :no) overrides that.

source
JuliaIR.HandlerNestingError — Type
JuliaIR.HandlerNestingError

The error thrown by LowerExcHandlers (jl-lower-exc-handlers) when a function leaves more exception handlers than it entered, or leaves a number of them that isn't a constant. The function is not changed.

source
JuliaIR.LowerSIMDLoopPass — Function
JuliaIR.LowerSIMDLoopPass()

Lower the loop markers of Julia's @simd (jl-lower-simdloop in a pipeline; a loop pass, for loop(...) and loop-mssa(...) pipelines). Julia marks the loop ID of a loop with julia.simdloop and, for @simd ivdep, julia.ivdep. The pass removes these markers, tags the memory accesses of ivdep loops with !llvm.mem.parallel_loop_access, and allows reassociating and contracting the floating-point reductions of simd loops. For the IR of Julia 1.12 and later, it also marks the multiplications that only feed an addition of a reduction as contract. Like Julia's C++ pass, it is skipped on optnone functions.

source
JuliaIR.ExpandAtomicModifyPass — Function
JuliaIR.ExpandAtomicModifyPass()

Lower the julia.atomicmodify.* calls that Julia emits for @atomic modify operations (jl-expand-atomic-modify in a pipeline). Such a call atomically replaces the value at a pointer by the result of a function of the old value, and returns the old and the new value. When that function is a single operation that atomicrmw supports (integer and floating-point addition and subtraction, bitwise operations, minimum and maximum, saturating subtraction, or exchange when it ignores the old value), it is inlined and turned into that atomicrmw, also when it reaches the operation through up to three calls that pass the old value on; otherwise the call to the function is wrapped in a compare-exchange loop.

Julia 1.13 introduced these calls, so the pass does nothing for the IR of earlier versions. Like Julia's C++ pass, it is skipped on optnone functions.

source
JuliaIR.AtomicModifyError — Type
JuliaIR.AtomicModifyError

The error thrown by ExpandAtomicModify (jl-expand-atomic-modify) for a julia.atomicmodify call it can't lower (where Julia's C++ pass crashes or emits invalid IR): its operation is not a function, its values are not integers, floating-point numbers or pointers, its ordering or synchronization scope is not a constant or the ordering is invalid, it needs a compare-exchange loop but its pointer has no alignment, or the inlined operation no longer corresponds to the atomicrmw it was matched to (e.g., because inlining it into a strictfp function made it a constrained floating-point intrinsic). The function is left unchanged by the errors of the first three kinds, which are checked before any call is lowered.

source
JuliaIR.CancellationLoweringPass — Function
JuliaIR.CancellationLoweringPass(; task_gcstack=0, task_ptls=0, task_eh=0,
                                 task_reset_ctx=0, tls_safepoint=0, reset_ctx_size=0,
                                 reset_ctx_align=0, reset_ctx_gcstack=0,
                                 reset_ctx_eh=0, reset_ctx_mctx=0, setjmp="")

Lower the cancellation points (julia.cancellation_point() calls, from Base.@cancel_check) that Julia 1.14 and later emit into reset regions (jl-cancellation-lowering in a pipeline, CancellationLowering in Julia's pipeline): at a point, the function publishes a stack buffer in its task, filled by setjmp, to which the runtime can jump back to deliver a cancellation; the pass closes the region again before every operation such a jump could tear, and before returning. See the documentation for the details.

Julia releases up to 1.13 don't have cancellation points, so for their IR the pass does nothing. Like Julia's pass, it also runs on optnone functions.

The lowering needs the layout of the runtime's task and reset context and the name of its setjmp, which are taken from the running Julia (see JuliaIR.runtime_layout) only for functions that need them; the keyword arguments give these facts explicitly.

source
JuliaIR.CancellationLoweringError — Type
JuliaIR.CancellationLoweringError

The error thrown by CancellationLowering (jl-cancellation-lowering) for a cancellation point it can't lower: one in a function without a GC stack (a julia.get_pgcstack call in the entry block, or an argument with the "gcstack" attribute), or one that is invoked. The function is not changed.

Dialects and options

JuliaIR.Dialect — Type
JuliaIR.Dialect(julia::VersionNumber; fp16=:auto, bf16=:auto, gc_barrier=:stock)

The IR dialect emitted by Julia version julia. The passes process the IR of the running Julia, so they use Dialect(VERSION), with the policies of their options; constructing the dialect of another version is useful to inspect how the versions differ.

Every Julia version from 1.10 up to the newest version this package knows about has a dialect; a prerelease like v"1.13.0-DEV.123" has the dialect of the release it precedes. Newer versions, including the development version (Julia master), get the newest known version's dialect: a new minor version starts out emitting the same IR as its predecessor, and only diverges as changes land on master.

The dialect only describes Julia's IR. What depends on the version of LLVM (e.g., the signature of the lifetime intrinsics) is determined by the library the passes run on, see JuliaIR.library_facts.

The keyword arguments are policies, which are not determined by the Julia version:

  • fp16: whether DemoteFloat16 demotes half arithmetic to float. :auto follows the rule of the Julia version (fp16_rule), :keep and :demote override it, including the function attributes that rule reads.
  • bf16: the same for bfloat arithmetic.
  • gc_barrier: the GC write-barrier configuration Julia was built with (:stock, :snapshot, :field_precise or :snapshot_field_precise).
source
JuliaIR.PassOptions — Type
JuliaIR.PassOptions

The options of one occurrence of a pass in a pipeline: the JuliaIR.Dialect of the IR (dialect, the running Julia's, with the policies of the options) and the pass-specific options (extra, a NamedTuple).

source
JuliaIR.parse_options — Function
JuliaIR.parse_options(str; fp16=:auto, bf16=:auto, gc_barrier=:stock, extra=(;))

Parse the option text of a pass in a pipeline (the part between < and >, e.g. fp16=demote;strong) into JuliaIR.PassOptions, whose dialect is the running Julia's. Options are separated by ;. The keyword arguments are the defaults for options that are not given. extra holds the defaults of the pass-specific options, which determine how they are parsed: a Bool option is written name or no-name, a Symbol option name=value. Unknown and repeated options are rejected.

Runtime facts

JuliaIR.runtime_layout — Function
JuliaIR.runtime_layout(dialect::Dialect, mod::LLVM.Module; facts...)
JuliaIR.runtime_layout(opts::PassOptions, mod::LLVM.Module)

The facts about the runtime of Julia dialect that passes processing mod need, as a JuliaIR.RuntimeFacts whose properties are the facts:

  • the layout of a task (task_gcstack, task_ptls, task_eh and, from Julia 1.14 on, task_reset_ctx) and of the thread-local state (tls_safepoint, tls_gc_state), as byte offsets;
  • exception handlers: handler_size and handler_align (of jl_handler_t) and the name of the runtime's setjmp; from Julia 1.14 on, the reset context (reset_ctx_size, reset_ctx_align and the offsets reset_ctx_gcstack, reset_ctx_eh, reset_ctx_mctx);
  • thread-local storage: tls_elf_support and the thread-pointer assembly tp_asm.

A fact is resolved when it is read, in order: from the keyword argument (pass option) of the same name, which gives it explicitly; from the running Julia, if dialect is its own; otherwise a JuliaIR.RuntimeError that names the fact and the option. Like Julia's own passes, the running Julia's facts are used whatever target mod is for (IR for targets without Julia's runtime, like GPUs, doesn't need them).

With PassOptions, the facts given explicitly come from the pass's options (see JuliaIR.runtime_options).

Type lowering

JuliaIR.julia_type — Function
JuliaIR.julia_type(T; allow_boxed=false, no_boxing=false)::LLVMType

The LLVM type that Julia's code generator uses for values of the Julia type T, in the current context (which must use opaque pointers): a port of Julia's julia_type_to_llvm, giving the same types as convert(LLVMType, T) does in a context of Julia's own LLVM, but in any context, e.g. of another LLVM library.

The result depends on the running Julia: it is built from the layout of T that the running Julia computed, never from a data layout. Values of types that Julia boxes are lowered to ptr addrspace(10), which is an error unless allow_boxed is set.

With no_boxing=true, T is lowered like an immutable type even if it is mutable or abstract, as by Julia's jl_struct_to_llvm (which Enzyme uses); the result can still be boxed (for Memory, for example). Types for which Julia's C++ would abort throw an ArgumentError instead: types with atomic fields, types without a layout and types without a fixed layout.

See also JuliaIR.isboxed and JuliaIR.julia_struct_type.

source
JuliaIR.isboxed — Function
JuliaIR.isboxed(T)::Bool

Whether JuliaIR.julia_type lowers values of type T to a pointer to a boxed object. This is not the calling convention: whether a function receives an argument of type T as a box is JuliaIR.deserves_argbox (a struct with an undefined reference field is lowered unboxed but passed boxed, for example).

source
JuliaIR.julia_struct_type — Function
JuliaIR.julia_struct_type(T; llvmcall=false, allow_boxed=false)::LLVMType

The structural representation of a value of type T that Julia's code generator uses when calling C (ccall, @cfunction) and for intrinsics: a port of _julia_struct_to_llvm. Unlike JuliaIR.julia_type, T is not checked to be a concrete immutable type first, and with llvmcall=true the result is the variant that ccall(..., llvmcall, ...) declares: Bool is i1, and structs (but not tuples) whose fields have the same LLVM type are LLVM structs rather than arrays. This is no ABI classification for C calls, which Julia's code generator does separately.

source
JuliaIR.deserves_stack — Function
JuliaIR.deserves_stack(T)::Bool

Whether Julia's code generator keeps values of type T unboxed, passing arguments and returning results of that type by value (or by reference to a stack copy) rather than as boxed objects: concrete immutable types that are singletons or can be stored inline. A port of deserves_stack in Julia's src/codegen.cpp.

source
JuliaIR.deserves_argbox — Function
JuliaIR.deserves_argbox(T)::Bool

Whether functions that Julia compiles receive arguments of type T boxed (as ptr addrspace(10)): !deserves_stack(T).

source
JuliaIR.deserves_retbox — Function
JuliaIR.deserves_retbox(T)::Bool

Whether functions that Julia compiles return values of type T boxed: !deserves_stack(T).

source
JuliaIR.deserves_sret — Function
JuliaIR.deserves_sret(T, llvmT::LLVMType)::Bool

Whether a function that returns an unboxed T, lowered to llvmT, returns it through a pointer argument (sret): values larger than a pointer that are neither floating-point nor vector values.

source
JuliaIR.check_layout — Function
JuliaIR.check_layout(T, dl::LLVM.DataLayout)::Vector{JuliaIR.LayoutDivergence}

Compare the layout the running Julia uses for values of type T with the layout that the data layout dl gives the LLVM type JuliaIR.julia_type lowers T to, and return the differences: the size, allocation size and alignment of T, and the offset of every field that occupies memory, with the size and alignment of the field's value (recursively for inline fields). An empty result means that code generated for dl addresses values of type T like Julia does.

Julia's code generator addresses fields by byte offsets that it maps onto the LLVM type's elements, so a divergence means that Julia's C++ also generates wrong code for that type and target. The lowering itself never consults a data layout; this is a diagnostic. Under the data layout of the running Julia's own target nothing diverges; GPU targets diverge for some types, see the documentation.

source
JuliaIR.LayoutDivergence — Type
JuliaIR.LayoutDivergence

A difference between the layout of a Julia type and the layout of the LLVM type it is lowered to, under some data layout, as found by JuliaIR.check_layout.

  • path: where in the type, e.g. "I128.b";
  • property: :size (the bytes a value occupies, sizeof, which must cover the bytes LLVM stores and fit in what it allocates; the value given for LLVM is the bound that is violated), :allocation_size (the distance between consecutive values in an array: sizeof rounded up to the alignment vs. LLVM's allocation size), :alignment, :offset (of a field, or of the selector byte of an inline union), or :pointer_size (of a reference);
  • julia and llvm: the two values, in bytes.

Libraries

JuliaIR.require_opaque — Function
JuliaIR.require_opaque(ctx::LLVM.Context)

Throw an error if ctx uses typed pointers. The passes only support opaque pointers; IR with typed pointers (as emitted by Julia 1.10) needs to be parsed into a context that uses opaque pointers, e.g. Context(; opaque_pointers=true), which upgrades it.

source
JuliaIR.library_facts — Function
JuliaIR.library_facts(ctx::LLVM.Context)

What the passes need to know about the LLVM library that ctx belongs to, as opposed to the Julia dialect of the IR:

  • llvm: the version of LLVM;
  • lifetime_size: whether the lifetime intrinsics take a size argument (before LLVM 22);
  • masked_load_alignment: whether llvm.masked.load and llvm.masked.gather take an alignment argument (before LLVM 22);
  • null_pointer_alignment: whether LLVM's Value::getPointerAlignment takes a null pointer to have the maximum alignment (before LLVM 22; later, only integer constants cast to pointers have a known alignment).
